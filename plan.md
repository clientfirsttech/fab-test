- **`.pbip` discovery walks trees the scanner prunes** — [`_pbip_discovery`](src/fabric_ci_cd_dataops/scripts/_pbip_discovery.py) calls `root.rglob("*.pbip")` and filters afterwards, so it descends into `.venv`, `node_modules`, `.git`, and every nested checkout: **9.7 s against `C:\Users\jkers\Git` versus 0.08 s** for the suffix scan over the same tree. [`_scan`](src/fabric_ci_cd_dataops/scripts/_scan.py)'s own docstring already records why it chose `os.walk` over `rglob` — *"`rglob` has no way to say 'do not descend'"* — and the sibling module does it anyway, so the two now hold different answers to "what is pruned". Latent, not user-visible: it sits in the *enrichment* path, and an artifact is found by its folder suffix, not by a paired `.pbip`. It bites `--dry-run` and `local` against a large root that does contain artifacts. Cut from Empty Discovery Diagnostics on 2026-08-22 as off-centre for that epic; the fix is to route it through the shared pruning walker.

- **Wire up the Power BI Desktop Bridge CLI** — deferred from Local Desktop First Run tasks 6-8. `doctor --local` already detects the bridge's presence (path only), but report-render capture (`invoke_desktop_report.py`, screenshot storage) needs its actual `status`/`screenshot`/`screenshot-all` command output schema, which couldn't be verified from the npm README (blocked) or any example output, and there's no live Desktop session in this environment to check against. Revisit once the schema is confirmed from a real installation or Microsoft's docs stabilize (currently preview, dated July 2026).

- [Playwright Embed Token Type](tasks/archive/2026-08-24-playwright-embed-token-type.md) — Every `fab-test playwright` run against a real workspace failed with a bare render timeout, behind two stacked defects that only the real CLI could separate. `embed_config` declared `tokenType = 0` under a comment reading `models.TokenType.Embed`; `0` is `Aad`, so a valid embed token was announced as an AAD token and the embed host went looking for the caller's home cluster — the 403s against `globalservice/clusterdetails` and `metadata/cluster/clienttelemetryrouting` that the console evidence had been reporting all along. Fixing that made the report render and *still* time out: the spec installed its container with `page.set_content()`, which performs `document.open()` and so removes every window event listener, including the `WindowPostMessageProxy` listener the Power BI service uses to receive events from the embed iframe. The iframe renders regardless, so the race waited out the full budget on a report that was visibly fine. Measured A/B against the live workspace, same report: with `set_content` 6 postMessages arrive and **0** SDK events fire; without it, `loaded` at 8.7 s and `rendered` at 12.5 s. 6/6 tasks; **1379 passed, coverage 85%**; verified through the real entry point — `fab-test playwright --env DEV` → passed, 1 case, 17.31 s, 0 findings, no 403s. The unit test had asserted `tokenType=0` against a hand-written constant — a mirror of the bug rather than a guard, green for any value — so it is replaced by a pinned contract test plus an `integration`-marked test that parses `TokenType`/`Permissions`/`ViewMode` out of the real CDN bundle and skips when offline. A prior attempt at this bug blamed Chromium's same-origin policy and shipped `--disable-web-security` plus a 60 s→180 s / 120 s→200 s timeout raise on a green unit suite alone; the passing A/B needs neither, and all of it is reverted here. Two things found and deliberately not chased: a benign 400 on `conceptualschema?userPreferredLocale=` (empty locale parameter, report renders and passes), and the reference implementation's other two divergences — a fresh `pbi.service.Service` instead of the `window.powerbi` singleton, and `document.body` listeners instead of `report.on(...)` — which the A/B retired as unnecessary once the listener survives.
