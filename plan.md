Also corrects the message's *"or `.pbip` projects"* clause, which offers a `.pbip` as a route to being found; it stopped being one when discovery went suffix-based. **4 tasks.**



## Standalone Tasks

- **Audit what the pipeline deletion stranded** — removing the nine Fabric pipeline workflows left several modules under `src/fabric_ci_cd_dataops/scripts/` with tests but no production caller: `detect_changes.py`, `deploy.py`, `check_promotion_safety.py`, `generate_fabric_cicd_config.py`, `compare_baseline.py`, `scan_credentials.py`, `scan_entropy.py`, and `aggregate_security_findings.py`. Each was invoked only by a workflow that no longer exists, so a green suite now proves only that dead code still parses. Not all of them are dead — `detect_changes.py` still produces the `changed-artifacts.json` that `playwright_validation/impact.py` consumes, and the TestPyPI epic already has a requirement to route its artifact-map loader through the shared metadata layers. Deliberately left out of the deletion commit: reachability needs checking one module at a time against the CLI, and a wrong call here deletes something a consumer reaches through a path nobody grepped for. Two smoke harnesses in the same position (`smoke_test_orchestrator.py`, `smoke_test_pql_test.py`, 778 lines and two published console scripts driving the deleted `orchestrator.yml`) were resolved with the deletion rather than deferred, because their run path was provably dead while `--help` kept passing in CI.

- **`.pbip` discovery walks trees the scanner prunes** — [`_pbip_discovery`](src/fabric_ci_cd_dataops/scripts/_pbip_discovery.py) calls `root.rglob("*.pbip")` and filters afterwards, so it descends into `.venv`, `node_modules`, `.git`, and every nested checkout: **9.7 s against `C:\Users\jkers\Git` versus 0.08 s** for the suffix scan over the same tree. [`_scan`](src/fabric_ci_cd_dataops/scripts/_scan.py)'s own docstring already records why it chose `os.walk` over `rglob` — *"`rglob` has no way to say 'do not descend'"* — and the sibling module does it anyway, so the two now hold different answers to "what is pruned". Latent, not user-visible: it sits in the *enrichment* path, and an artifact is found by its folder suffix, not by a paired `.pbip`. It bites `--dry-run` and `local` against a large root that does contain artifacts. Cut from Empty Discovery Diagnostics on 2026-08-22 as off-centre for that epic; the fix is to route it through the shared pruning walker.

- **Wire up the Power BI Desktop Bridge CLI** — deferred from Local Desktop First Run tasks 6-8. `doctor --local` already detects the bridge's presence (path only), but report-render capture (`invoke_desktop_report.py`, screenshot storage) needs its actual `status`/`screenshot`/`screenshot-all` command output schema, which couldn't be verified from the npm README (blocked) or any example output, and there's no live Desktop session in this environment to check against. Revisit once the schema is confirmed from a real installation or Microsoft's docs stabilize (currently preview, dated July 2026).

## Completed Epics

- [Playwright Through The Front Door](tasks/archive/2026-08-23-playwright-front-door.md) — `fab-test playwright` now refuses before any client or network call when its service principal is incomplete, naming every missing variable and where to set it, exiting `127` rather than running two API calls deep into a raw msal traceback; `doctor` reports it not-ready for the same reason instead of a false green (an ambient `az login`, unlike `pql-test`, cannot generate an embed token). Any other exception during embed-context acquisition now writes an error envelope and `::error::` instead of escaping as a traceback — including one surfaced only by live-testing this epic's own end-to-end verification, in the config/service-client resolution step ahead of it. `environments.yml` is optional once a workspace already resolves from `--workspace-id`, `FABRIC_WORKSPACE_ID`, or `workspace:` in `fab-test.yml`; that key is now discoverable via `fab-test init`'s scaffold and `config --show`. `resolve_item`'s "no match" message now names the closest candidates the workspace actually has, capped for an 80-column terminal, and lists the workspace once instead of twice. This repository re-aligned onto the layout a consumer is told to use: the four byte-identical files and the zero-caller `testbed.json` are gone from `.github/metadata/`, `environments.yml` moved to `.fab-test/metadata/`, and `analyzers.json`'s hardcoded rules paths resolve through the metadata layers like everything else. `.env` discovery is unified across `_credentials.py` and the Playwright config loader (`--env-file` > `PLAYWRIGHT_ENV_FILE` > `.fab-test/.env` > `./.env`), with `fab-test init` now scaffolding `.fab-test/.gitignore` and `.fab-test/.env.example` so a real secret is never one `git add .fab-test/` away from being committed. 8/8 tasks; **1317 passed, coverage 84%** (from prior baseline); end-to-end verified through the real CLI with a fake service principal — the whole chain (config, workspace resolution, metadata layers, service-client build) reaches the genuine Azure AD boundary and fails as a clean envelope rather than a traceback. Not verified live: an actual passing envelope, since no real Fabric tenant or deployed workspace is available in this environment. One pre-existing, out-of-scope defect found and recorded, not fixed: `_resolve_workspace_target` in `fab_test.py` unconditionally builds a Fabric service client whenever a `workspace:`/target name is present, even when it is already a GUID that `resolve_workspace_id` would short-circuit without one.

- [Eventhouse Shipping](tasks/archive/2026-08-22-eventhouse-shipping.md) — `fab-test` used to report that it sent telemetry and send nothing: `publish_to_eventhouse` printed a banner ending `✅ TELEMETRY LOGGING SIMULATION COMPLETED` and returned `True`, so even the handler that would have warned was told it worked. Now there is a wire. `fab-test.yml` carries `telemetry.eventhouse.uri`/`.database` — which it could not before, since `additionalProperties: false` made a `telemetry:` block a validation *error* — resolved through the same env > file > default chain and reported by `config --show`. **A configured destination is the enablement; there is no new flag**, and `--telemetry` with nowhere to send now exits `2` instead of quietly reaching the placeholder. Ingest reuses the service principal the CLI already resolves (`DefaultAzureCredential` fallback, partial principal refused) via a new `resolve_service_principal` in `_credentials` rather than a third copy of that logic. Records batch per run — `_send_telemetry` is called per artifact, so the obvious port would open a queued-ingest client N times. The Kusto SDK ships as `pip install 'fab-test[telemetry]'`. Failure never changes an exit code, warns once per run rather than once per artifact, and lands in `run.json`'s new `telemetry_error`. Two defects were found by running the installed console script and none by the suite: `DataFormat` lives in `azure.kusto.data`, not `.ingest`, and queued ingest needs the `ingest-` host prefix. `eventhouse_logger.py` came off the coverage omit list — it was listed as needing a live service, which was true of the ingest and never of the validators in front of it, and being omitted is how they went entirely untested (now 26 tests, module 33% → 58%). 9/9 tasks; **verified end to end against a real Eventhouse** — five records delivered and confirmed queryable, routed correctly across both tables, authenticated through the `DefaultAzureCredential` fallback. The live test earned its keep: the tables carry one `Data: dynamic` column with a fixed ingestion mapping, and without that mapping Kusto matches nothing by column name and stores empty rows while reporting success.
