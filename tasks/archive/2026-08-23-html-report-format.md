## Overview

Today's HTML reports are useful when something fails but hard to trust when nothing does — BPA and pql-test reports show only violations, so a passing run renders as an empty "No findings" page with no evidence of what was actually checked, and the main index report has no timestamp or run identity (user/branch/commit) to anchor it in time. Meanwhile the PBIR report — generated by a third-party vendor tool, not by fab-test — already shows every test with a working filter/drill-down UI, but ships with a broken favicon link, and its filter pattern (jQuery + CDN scripts) can't simply be copied into fab-test's deliberately dependency-free renderer. This epic closes both gaps: extend the shared renderer (`_report_html.py`) so BPA and pql-test carry and display full pass/fail results with a self-contained filter-by-severity control matching the *spirit* of PBIR's UX (not its implementation), stamp the main report with timestamp + git identity with a safe non-git fallback, fix the PBIR favicon, and document the extension points so a future contributor can add a new analyzer's report without re-deriving the pattern.

**Guardrails this epic must respect** (from `vision.md` and `tasks/archive/2026-08-21-human-readable-reports.md`):
- **Facade, not fork**: no new judgment gets computed for the report — only data already produced (test results, pass/fail counts, git state) gets *displayed* differently.
- **No external dependencies**: reports stay self-contained — no CDN scripts, no `<script src>`, no external `<link>`. `tests/test_report_html.py` already asserts this; any filter UI must use inline `<style>`/vanilla inline `<script>` or pure CSS (e.g. radio-driven `:checked` selectors), not a JS framework.
- **Determinism**: existing tests assert reports are byte-identical across runs given the same inputs (`tests/test_report_html.py`, `tests/test_report_timestamp.py`). A timestamp is inherently non-deterministic — this epic must decide, explicitly, where that's acceptable (index/run-level report) and where it isn't (per-analyzer `report.html`), and update/extend those tests rather than break them.
- **Three-caller contract**: human (readable HTML), pipeline (still machine-parseable envelope/exit codes), agent (skill docs) — none should regress.

## Fix broken image link in PBIR report

The generated `TestRun.html` (e.g. `analyzer-results/pbir/<artifact>/native.json/TestRun.html`) references its favicon as `<link rel="icon" href="../icon/pbiinspector.png">` (from `TestRunTemplate.html:18`), a relative path that resolves against the output directory where the html actually lands — `analyzer-results/pbir/icon/pbiinspector.png` — which is never created there. The source icon only exists under the vendor install path (`.fab-test-tools/pbir_inspector/extracted/linux-x64/FabInspCLI/Files/icon/pbiinspector.png`). The template already proves the fix pattern works: its `%LOGO%` placeholder and per-page wireframe PNGs are inlined as base64 `data:image/png;base64,...` URIs and render fine.

Because `TestRunTemplate.html` is a vendored, third-party file (FabInspCLI), the fix should live in the copy/wiring step, not by hand-editing vendor source: `invoke_pbir_inspector.py` currently only globs for `TestRun.html` in place and records its path (`native_out.glob("*.html")` and `native_html_output_path`, ~lines 456-473, 498) — it never post-processes the file. Add a small post-processing step there that either (a) inlines the favicon as a base64 data URI directly into the discovered html (rewriting the `<link rel="icon" href="../icon/...">` tag), or (b) copies `Files/icon/pbiinspector.png` next to each generated `TestRun.html` and rewrites the href to a same-directory relative path. Prefer (a) — it needs no extra file alongside the report and matches the existing inlining precedent in the same template.

**Requirements**:
- Given a PBIR test run produces `TestRun.html`, when the file is opened directly from its output directory, then the favicon should load without a 404/broken-link, with no manual asset copy required.
- Given the vendor template changes its icon reference in a future FabInspCLI update, then the fix should degrade gracefully (log/skip) rather than crash the pbir-test subcommand if the expected `<link rel="icon" ...>` pattern is not found.
- Given this fix touches vendor output rather than vendor source, then it must not modify files under `.fab-test-tools/` — only the generated `TestRun.html` copy that ships in `analyzer-results/`.

## Add run metadata to the main report

`render_index`/`write_index` (`_report_html.py:181-246`, invoked from `fab_test_summary.py:719-722`) currently renders only per-analyzer summaries and links, with no run-level timestamp or identity. Reusable git-context resolution already exists — `_git_context()`/`_git_command_output()` in `fab_test.py:436-470` — which reads CI env vars first (`GITHUB_REPOSITORY`, `GITHUB_REF_NAME`, `GITHUB_SHA`, `GITHUB_ACTOR`, `GITHUB_RUN_ID`) and falls back to local `git rev-parse HEAD`, `git rev-parse --abbrev-ref HEAD`, `git config user.email`, swallowing failures when not in a git repo at all. Reuse this rather than reimplementing git plumbing.

Add a metadata header to the index page: generated-at timestamp (UTC, explicit `Z` suffix), user/actor, branch, short commit SHA — each field rendered as `—` or omitted cleanly when unavailable (non-git checkout, shallow clone, detached HEAD).

This *does* introduce non-determinism into the index page specifically. Resolve the tension with existing determinism tests by scoping the change: per-analyzer `report.html` (produced by `render_report`, whose docstring at lines 96-103 explicitly argues against timestamps) stays untouched and deterministic; only the run-level `index.html` gains a metadata header, since it represents one specific run rather than a reusable/comparable artifact. Existing determinism tests in `tests/test_report_html.py`/`tests/test_report_timestamp.py` that cover `render_report()` are unaffected; index-specific tests will need a new fixture that either freezes/injects the timestamp (parameter, not `datetime.now()` inline) or explicitly asserts the header's presence/shape rather than exact equality.

**Requirements**:
- Given `write_index()` runs, then the rendered page should show a UTC timestamp of when the report was generated.
- Given the run happens inside a CI job with `GITHUB_*` env vars set, then the metadata should show actor, branch (`GITHUB_REF_NAME`), and commit SHA (`GITHUB_SHA`) sourced from those, not local git.
- Given the run happens in a local git checkout with no CI env vars, then the metadata should fall back to `git` plumbing (`_git_context()`) for user/branch/commit.
- Given the run happens outside any git repository (e.g. an extracted zip, no `.git`), then metadata fields should render a safe placeholder (e.g. `—` or "unknown") instead of raising or crashing report generation.
- Given `render_index()` accepts an explicit timestamp/metadata parameter (not a hidden `datetime.now()` call), then a test can inject a fixed value and assert deterministic output for a given input.

## Carry full test results into BPA and pql-test envelopes

Both analyzers currently discard passing/skipped results before they ever reach the report. `invoke_pql_test.py:116-122` filters `findings` to only failed, non-skipped rows, and `invoke_pql_test.py:384-397` writes an *empty* findings list to the envelope whenever the overall run status isn't `"failed"` — even though `_summarize_results`/`test_summary`/`test_results` (lines ~123-132) already compute full pass/fail/skip data upstream. `invoke_tabular_editor_bpa.py`'s `_bpa_findings` (~line 328) similarly builds findings only from failed TRX results. In both cases the full-results data already exists in-process; it's just not threaded through to `write_results`/the envelope.

Add a new envelope field — e.g. `test_results` (list of `{name, status: pass|fail|warning|skip, detail, rule/path context}`) — populated from the data both analyzers already compute, written unconditionally (pass or fail), alongside the existing `findings` field (which stays failure-only, since other consumers — terminal summary, exit-code logic, CI gating — depend on that meaning today). This is additive, not a breaking change to the envelope schema: `normalize_findings()` in `_analyzer_envelope.py:82` and any code reading `findings` is untouched.

**Requirements**:
- Given a pql-test run where all tests pass, then the envelope should still contain a `test_results` entry for every test executed, not zero entries.
- Given a BPA run, then the envelope's `test_results` should include every rule evaluated against every item, with a status of pass/fail/warning, not only violations.
- Given existing code paths that read `findings` (terminal summary, exit codes, CI gating, `normalize_findings()`), then their behavior must be byte-for-byte unchanged — `test_results` is additive only.
- Given the new field's shape, then it should be documented in `.github/skills/fab-test/SKILL.md`'s envelope-keys reference so both humans and the fab-test skill agree on it.

## Extend the shared renderer with a self-contained filter-by-status control

With full results available in the envelope, extend `render_report()` in `_report_html.py` to render a complete test list (when `test_results` is present) with a status column, alongside the existing failure-only findings table (kept for backward-compatible callers/tests that only ever populated `findings`). Add a filter control — pure CSS, no JS, no CDN — using the classic radio-input + `:checked` sibling-selector pattern (hidden radio buttons acting as tabs: "All / Errors / Warnings / Passed") to show/hide table rows by a `data-status` attribute, keeping the report self-contained per the existing `test_report_html.py` "no external script/link" assertions. This mirrors PBIR's filter *experience* without importing PBIR's jQuery/CDN implementation.

Design this as one reusable renderer function/table partial (not three copies) so BPA, pql-test, and any future analyzer opt in identically by populating `test_results` — this is the concrete "extensibility" mechanism the epic promises: a new analyzer author needs only to populate the shared envelope field, not write new HTML.

**Requirements**:
- Given an envelope with a populated `test_results` field, then `render_report()` should render a full table of all tests with a visible status per row (pass/fail/warning/skip).
- Given the rendered report, then a filter control should let the viewer switch between All / Errors / Warnings / Passed without a page reload, implemented with zero external JS/CSS dependencies.
- Given an envelope with only the legacy `findings` field (no `test_results`) — e.g. an older analyzer that hasn't adopted the new field yet — then the report should render exactly as before, with no filter control and no broken layout.
- Given `tests/test_report_html.py`'s no-external-resource assertions, then the new filter markup must still pass them unmodified in intent (self-contained HTML/CSS only).
- Given BPA and pql-test both populate `test_results` per the prior task, then both of their reports should show the new full-list + filter UI using the exact same renderer code path (no per-analyzer HTML branching).
